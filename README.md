# Гибридная система медицинских записей (SQLite + MongoDB)

Консольное приложение на Python, демонстрирующее **полиглотную персистентность**
(polyglot persistence): одновременное использование реляционной и нереляционной
баз данных, каждая из которых решает свою задачу.

- **SQLite** — хранит строго структурированные сущности: пациентов и врачей.
- **MongoDB** — хранит медицинские записи (диагноз, заметки, результаты
  анализов), структура которых отличается от визита к визиту.

Проект выполнен в рамках практического задания по нереляционным базам данных.

---

## Требования

- Python 3.9+
- Библиотеки: `pymongo`, `mongomock`

## Функционал

После запуска доступно консольное меню:

| Пункт | Действие | Используемая БД |
|:---:|---|---|
| 1 | Добавить пациента | SQLite |
| 2 | Добавить врача | SQLite |
| 3 | Добавить медицинскую запись | SQLite + MongoDB |
| 4 | Список пациентов | SQLite |
| 5 | Список врачей | SQLite |
| 6 | Полная история пациента | SQLite + MongoDB |
| 7 | Поиск по диагнозу | MongoDB (regex) |
| 0 | Выход | — |

### Подробнее по пунктам

**1. Добавить пациента.** Запрашивает ФИО, дату рождения и телефон.
Телефон можно пропустить.

**2. Добавить врача.** Запрашивает ФИО и специализацию.

**3. Добавить медицинскую запись.** Сначала показывает списки пациентов и
врачей с их ID, затем запрашивает ID пациента и врача, диагноз, заметки,
результаты анализов в формате `ключ=значение, ключ=значение`
(например, `pressure=150/95, cholesterol=6.2`) и дату визита
(если пусто — ставится текущая). Запись сохраняется в MongoDB, ссылки на
пациента и врача — по их `id` из SQLite.

**4. / 5. Списки пациентов и врачей.** Показывают всех сохранённых в SQLite.

**6. Полная история пациента.** Пример **кросс-БД запроса**: по ID пациента
из SQLite достаётся его карточка, а по `patient_id` из MongoDB — все его
медицинские записи. Для читаемости для каждой записи подтягивается ФИО врача
из SQLite.

**7. Поиск по диагнозу.** Регистронезависимый поиск по подстроке в поле
`diagnosis` всех документов коллекции `medical_records` (использует `$regex`
в MongoDB).

## Структура данных

### Реляционная часть (SQLite, файл `medical.db`)

```sql
CREATE TABLE patients (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    full_name  TEXT NOT NULL,
    birth_date TEXT NOT NULL,
    phone      TEXT
);

CREATE TABLE doctors (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    full_name      TEXT NOT NULL,
    specialization TEXT NOT NULL
);
```
Обе таблицы — классические сущности со строгой схемой и типизированными
полями.

### Нереляционная часть (MongoDB, коллекция `medical_records`)

Один документ:

```json
{
  "_id":          "…",
  "patient_id":   1,
  "doctor_id":    2,
  "visit_date":   "2024-02-10",
  "diagnosis":    "Гипертония I степени",
  "notes":        "Повышенное давление, контроль АД",
  "test_results": {
    "pressure":    "150/95",
    "cholesterol": 6.2
  }
}
```

У другого документа той же коллекции поле `test_results` может выглядеть
совершенно иначе:

```json
"test_results": {
  "ecg":        "синусовая аритмия",
  "heart_rate": 95
}
```
или
```json
"test_results": {
  "mri":        "без патологий",
  "pain_scale": 7
}
```

## Зачем здесь MongoDB

Главная причина — **у медзаписей разная структура**. Результаты анализов на
разных визитах содержат разные поля:

| Визит | Поля в `test_results` |
|---|---|
| Кардиолог | `pressure`, `cholesterol` |
| Терапевт при ОРВИ | `temperature`, `crp` |
| Невролог | `mri`, `pain_scale` |
| Кардиолог (ЭКГ) | `ecg`, `heart_rate` |

В реляционной модели все варианты плохие:

- **Отдельная таблица под каждый тип анализа** — число таблиц растёт с
  каждым новым обследованием, схема постоянно мигрирует.
- **Таблица EAV** (`record_id | attr | value`) — запросы громоздкие,
  типизация теряется: всё в одной текстовой колонке.
- **JSON-колонка** в реляционной БД — «MongoDB внутри PostgreSQL/MySQL»,
  реляционная СУБД используется не по назначению.

**MongoDB решает это естественно:** каждый документ несёт свой набор полей
в `test_results`, схема не нужна, миграции не требуются. Новый тип анализов =
новый ключ в документе.

Дополнительно:

- **Слабая связность.** У записи только `patient_id` и `doctor_id`, между
  собой записи не связаны — нормализация и внешние ключи не нужны.
- **Гибкий поиск.** Пункт 7 — regex-поиск по диагнозу нативно средствами
  MongoDB, без `LIKE '%...%'` и его проблем с производительностью.
- **Развитие схемы.** Новое поле (`allergies`, `referral`) добавляется без
  миграции: просто кладётся в новые документы, старые остаются валидными.

## Итог

1. **Полиглотная персистентность** — две БД, каждая решает свою задачу.
2. **Кросс-БД запрос** (п. 6) — пациент из SQLite + история из MongoDB по
   `patient_id`.
3. **Гибкость документной модели** (п. 3) — разные `test_results` в одной
   коллекции без схемы.
4. **Нативный поиск** (п. 7) — regex по полю документа.

Архитектура: **Python → (SQLite для пациентов и врачей, MongoDB для
медзаписей)**.
